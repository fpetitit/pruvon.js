Introduction

Pruvon is inspired by Concordion: you write a spec describing expected behavior as plain HTML or Markdown, pair it with a small fixture module that wires each example to your real code, and Pruvon produces a result — the same document, with every example colored green or red.

Spec.pruvon.html / .pruvon.md
+
Fixture.pruvon.fixture.js
→
pruvon engine
→
Result.pruvon.result.html

This tutorial walks through that whole loop using one example: splitting a full name into a first and last name — the same example Concordion itself uses in its getting-started guide.

1

Discussing

Before writing anything executable, agree on the behavior in plain language with whoever cares about it — a teammate, a stakeholder, your own rubber duck.

"Jane Smith" → first name "Jane", last name "Smith"

"Ada Lovelace" → first name "Ada", last name "Lovelace"

(what about middle names? — out of scope for now)

2

Documenting

Write the agreed examples down as plain tables — no execution yet, just the shared understanding, saved as name-splitter.pruvon.html:

HTML 
<h2>First Name</h2>
<table>
    <tr><th>Full Name</th><th>First Name</th></tr>
    <tr><td>Jane Smith</td><td>Jane</td></tr>
</table>

Rendered in a browser, it's just a plain, uncolored table — a readable document on its own, before any code is involved:

3

Instrumenting

Add a data-execute attribute naming the fixture function to call for each row. Pruvon supports the same instrumented spec in HTML or Markdown — pick whichever your team is more comfortable authoring:

HTML — name-splitter.pruvon.html 
<table data-execute="firstName">
    <tr><th>Full Name</th><th>First Name</th></tr>
    <tr><td>Jane Smith</td><td>Jane</td></tr>
</table>
Markdown — name-splitter.pruvon.md 
```pruvon:firstName
| Full Name | First Name |
|---|---|
| Jane Smith | Jane |
```
How the Markdown fence works
A fenced code block tagged pruvon:<fnName> has its table content rendered and tagged data-execute="<fnName>"; everything else in the file renders as normal Markdown. See src/render-markdown.js.

The real implementation

JavaScript 
import { splitName } from '../../src/name-splitter.js';

export function firstName(args) {
  return splitName(args[0]).firstName;
}

export function lastName(args) {
  return splitName(args[0]).lastName;
}

Why two tables instead of one?
Concordion can chain several outputs (firstName and lastName) off a single row. Pruvon's row model is simpler — one expected value per row — so the same idea is expressed as two small tables, one per fixture function. See src/run-table.js.

Running it

The full example above (both the HTML and the Markdown version) lives in docs/examples/. Run it with the CLI:

$ npx pruvon --cwd docs/examples ✔ name-splitter.pruvon.md: 4 passed, 0 failed ✔ name-splitter.pruvon.html: 4 passed, 0 failed 8 passed, 0 failed
Exit code contract
0 — every row across every discovered spec passed (or no specs were found). 1 — any row failed, any fixture function threw, or a spec had no paired fixture — making pruvon usable directly as a CI gate (see .github/workflows/ci.yml in this repo).

Advanced

Async fixtures
Fixture functions may be async — Pruvon awaits every call, so a fixture backed by a database or an HTTP call works the same way.
One bad row doesn't ruin the run
Each row runs in its own try/catch. A throwing or missing fixture function only fails that row — every other row (in the same table, and in every other spec) still runs and reports normally.
